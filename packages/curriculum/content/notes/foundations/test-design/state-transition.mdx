**State transition testing** suits systems whose behaviour depends on **history**
— what happens next depends on the current state, not just the current input. Think
order lifecycles, media players, or authentication flows.

## The four ingredients

- **States** — the modes the system can be in (`Draft`, `Placed`, `Shipped`).
- **Events** — the triggers that cause a change (`submit`, `pay`, `cancel`).
- **Transitions** — event + current state → next state.
- **Actions** — side effects a transition produces.

## Example — an order

```
Draft ──submit──▶ Placed ──pay──▶ Paid ──ship──▶ Shipped
  │                 │
  └──cancel──▶ Cancelled ◀──cancel──┘
```

## What to test

- **Valid transitions** — every arrow in the diagram fires correctly.
- **Invalid transitions** — an event that *shouldn't* be allowed in the current
  state is **refused**, not silently accepted. (Can you `ship` a `Draft`? You
  must not be able to.) These negative paths are where the real defects hide.
- **State coverage** — every state is reached at least once.

A **state table** (states × events grid) makes the invalid transitions explicit:
every empty cell is a case that must be rejected.
