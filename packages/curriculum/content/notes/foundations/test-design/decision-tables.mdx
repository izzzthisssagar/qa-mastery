A **decision table** models logic where the output depends on **combinations** of
input conditions. It's the go-to technique for business rules — the kind of
"if this AND that but NOT the other" logic that's easy to under-test.

## Structure

Rows are split into **conditions** (inputs) and **actions** (outputs). Each
column is a **rule** — one combination of condition values and the action it
produces.

## Example — a discount rule

*Members get 10% off; orders over $100 get free shipping.*

| Condition | R1 | R2 | R3 | R4 |
|-----------|----|----|----|----|
| Member? | Y | Y | N | N |
| Order > $100? | Y | N | Y | N |
| **Action** | | | | |
| 10% discount | ✓ | ✓ | – | – |
| Free shipping | ✓ | – | ✓ | – |

Two conditions → 2² = **4 rules**, each a test case. Every combination is
visible, so you can't forget "member with a small order."

## Collapsing the table

When some conditions don't affect the outcome, mark them "–" (don't care) and
merge rules — this keeps large tables manageable. But add conditions carefully:
*n* conditions mean *2ⁿ* columns, so the table grows fast. If it explodes,
that's a signal the rule itself may be too complex.
