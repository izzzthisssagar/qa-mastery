A bug report is a *sales pitch* for a fix. Its job is to make the defect
**reproducible** and its **impact** obvious. The essential fields:

- **Title** — a one-line summary: *what* breaks, *where*. "Checkout total ignores
  discount code on mobile."
- **Environment** — build/version, OS, browser, device — anything that scopes it.
- **Steps to reproduce** — numbered and minimal. Strip everything that isn't
  needed to trigger the bug.
- **Expected result** — what should happen, per the requirement.
- **Actual result** — what actually happened.
- **Evidence** — screenshot, video, logs, network trace.
- **Severity vs priority** — see below.

## Severity vs priority

These are different axes and testers conflate them constantly:

- **Severity** — the *technical impact* if it occurs (crash > wrong data >
  cosmetic). Set by the tester.
- **Priority** — *how soon* it should be fixed given business context. Set by the
  team/PO.

A typo in the company name on the landing page is *low severity, high priority*.
A crash in an unused admin corner is *high severity, low priority*.

## The reproducibility test

Before you file it, delete a step and see if it still repros. The shortest set of
steps that reliably triggers the bug is the report you want — it respects the
developer's time and gets fixed faster.
