A **test case** is a repeatable experiment on the software. Anyone should be able
to run it and get the same verdict. The anatomy:

- **ID / title** — a short, searchable name (`TC-Login-01: valid credentials`).
- **Preconditions** — the state the system must be in before you start.
- **Test data** — the specific inputs used.
- **Steps** — numbered, atomic actions. One action per step.
- **Expected result** — the *single* observable outcome that decides pass/fail.
- **Priority** — how important this scenario is (drives execution order).

## Qualities of a good test case

- **Atomic** — verifies one thing. A case that checks five behaviours can't tell
  you *which* one failed.
- **Unambiguous** — "click Submit", not "submit the form somehow".
- **Independent** — doesn't rely on a previous case having run.
- **Traceable** — links back to a requirement or acceptance criterion.

## Positive and negative cases

For every "it works" case, write the "it fails gracefully" counterpart: empty
inputs, wrong types, boundary values, unauthorized access. Negative cases are
where most real defects hide.

## Example

> **TC-Login-02: locked account**
> **Precondition:** account `demo@x.dev` has 5 failed attempts.
> **Steps:** 1) Open /login. 2) Enter valid credentials. 3) Click *Log in*.
> **Expected:** an "account locked" message; no session is created.
